# UniBot 需求规格说明书

---

## 0. 文档说明

### 0.1 文档目的

本文档是 UniBot 项目的需求规格说明书（Software Requirements Specification, SRS）。其目的是：

1. 明确 UniBot 系统的功能需求、非功能需求和约束条件
2. 为后续数据库设计、架构设计、实现和测试提供统一的需求基线
3. 作为课程评审和开源社区理解本项目的权威参考

### 0.2 适用范围

本文档覆盖 UniBot 系统的全部需求，包括 Bot 调试与管理、协议报文追踪、消息与会话管理、社交资料镜像、审计与系统维护五个核心领域。本文档不包含系统安装和运维指南。

> **注**：本文档中的字段名和实体名用于表达需求约束和业务语义，不代表最终数据库表结构；最终表结构以数据库设计文档为准。

### 0.4 术语与缩略语

| 术语 | 定义 |
|------|------|
| **UniBot** | 本项目系统名称：一个面向 QQ Bot 的多 Bot 本地调试与管理平台 |
| **Bot** | 在 UniBot 中注册的机器人实例，绑定一个 IM 账号，由协议适配器驱动运行 |
| **IM Account** | 外部即时通讯平台账号，在本文档语境下主要指 QQ 账号，可来源于模拟端或真实协议端 |
| **Adapter** | 协议适配层，负责将外部协议（Milky / OneBot-v11 / OneBot-v12）的事件和 API 映射为 UniBot 内部统一模型 |
| **Protocol Packet** | 一次协议交互的完整记录，包含请求/响应/事件的元数据及原始 JSON 报文 |
| **Debug Session** | 一次 Bot 启动到停止的调试周期，用于聚合同一调试过程内的消息和协议包 |
| **Conversation** | 会话，用户视角的消息容器，抽象私聊、群聊、临时会话三种场景 |
| **Message Scene** | 消息所在的会话场景类型：private（私聊）、group（群聊）、temp（临时会话） |
| **Peer ID** | 会话对端标识，在群聊场景下为群 ID，在私聊/临时会话场景下为对方用户 ID |
| **Message Seq** | 消息在特定 scene + peer 内的单调递增序号，由协议端维护 |
| **Group** | QQ 群组，包含群资料、成员、公告、文件等子实体 |
| **Friend** | QQ 好友关系，含备注、分组、置顶等属性 |
| **Audit Event** | 系统级操作审计记录，记录谁在什么时间对什么实体做了什么操作 |
| **Simulated / Real** | 模拟/真实环境区分：simulated 由 UniBot 内置虚拟服务端产生，real 来自外部真实 QQ 协议端 |
| **Milky** | 一个 QQ 机器人应用接口标准，基于 HTTP/WebSocket，提供消息、事件、API 接口 |
| **OneBot** | 通用聊天机器人应用接口标准，v11 和 v12 版本在事件模型和 API 设计上有差异 |
| **Tauri** | 使用 Rust 后端 + Web 前端的跨平台桌面应用框架 |
| **SQLite** | 嵌入式关系型数据库，UniBot 的本地持久化存储引擎 |

## 1. 项目背景

### 1.1 QQ Bot 开发调试的痛点

QQ Bot 开发者在日常工作中面临以下问题：

1. **协议黑盒**：Bot 通过 Milky 或 OneBot 等协议与 QQ 服务端通信，协议请求/响应对开发者不可见，难以定位"消息发不出去""事件没收"等问题的根因。
2. **缺乏结构化调试工具**：开发者通常只能查看终端日志或抓包工具，缺少按 Bot、按会话、按时间组织的结构化协议报文浏览界面。
3. **多 Bot 管理混乱**：一个开发者可能同时维护多个 Bot 实例，每个 Bot 绑定不同 QQ 账号、使用不同配置、面对不同群组。缺少统一的管理界面。
4. **无消息与协议关联**：当用户反馈"Bot 没回复某条消息"时，开发者需要人工关联"那条消息对应的协议事件是什么""Bot 是否收到了该事件""Bot 发出的 API 调用是否成功"。
5. **模拟测试困难**：开发者需要在不影响真实 QQ 环境的前提下测试 Bot 行为，但缺少内置的模拟 IM 环境。

### 1.2 UniBot 的目标用户

UniBot 为以下人群设计：

- **QQ Bot 开发者**：使用 Milky / OneBot 等协议开发 QQ 机器人的个人或团队，需要调试消息收发、事件处理、API 调用的正确性。
- **Bot 运维管理者**：需要同时管理多个 Bot 实例的连接状态、配置版本、群组行为策略。

### 1.3 UniBot 的核心价值主张

**UniBot 是一个面向 QQ Bot 的多 Bot 本地调试与管理平台。**

它通过选择性镜像与 Bot 调试相关的 QQ 数据（消息、会话、群组、好友资料及关键协议事件），为开发者提供"从用户视角看到的消息 → Bot 收到的协议事件 → Bot 发出的 API 调用"的全链路可追溯调试体验。所有数据完全本地化存储，保护隐私安全。

## 2. 项目定位

### 2.1 系统定位

UniBot 定位为**多 Bot 本地调试与管理平台**，系统形态为基于 Tauri 的桌面应用。

核心逻辑链路：

```
外部协议端（Milky / OneBot）
        ↓ 事件 & API 响应
UniBot Adapter 层（归一化）
        ↓
本地数据库 + 文件系统（全量存储）
        ↓
React 前端界面（Bot 管理 / 消息会话 / 协议追踪 / 审计）
```

UniBot 不是：

- 一个生产级 Bot 托管云平台
- 一个完整的 QQ 客户端替代品
- 一个长期聊天记录归档系统

### 2.2 核心能力

| 编号 | 能力 | 说明 |
|------|------|------|
| C1 | **多 Bot 管理** | 注册、启动、停止多个 Bot 实例，管理 Bot 与 IM 账号的绑定关系 |
| C2 | **消息会话管理** | 按会话组织消息，支持私聊/群聊/临时会话三种场景，维护未读状态和会话列表 |
| C3 | **调试上下文镜像** | 按调试需要缓存好友、群组、群成员及协议端返回的低频资料，用于支撑消息展示、Bot 行为调试和协议追踪 |
| C4 | **协议报文追踪** | 全量记录每一次协议交互的元数据和原始 JSON，支持按 Bot、时间、错误状态筛选 |
| C5 | **调试会话聚合** | 将一次 Bot 运行周期内的消息和协议包聚合为可回看的调试会话 |
| C6 | **配置管理** | 管理 Bot 的连接配置和行为配置，记录配置变更历史 |
| C7 | **审计与安全** | 记录所有关键操作，支持审计追溯和数据清理 |

### 2.3 非目标概述

UniBot 明确不追求以下目标：

1. UniBot 不是 QQ 客户端的完整替代品，不保证同步全部历史消息
2. UniBot 不提供跨设备多用户协作能力
3. UniBot 不作为生产级云托管 Bot 平台
4. UniBot 不直接管理 QQ 登录凭据（由协议端自行管理）
5. UniBot 不保证跨协议端字段的完全一致性

详见第 10 章不做范围的正式条目列表。

## 3. 约束与上下文

### 3.1 外部协议约束

UniBot 的核心功能依赖外部协议端提供的事件和 API。系统需支持以下协议：

| 协议 | 版本 | 通信方式 | 说明 |
|------|------|----------|------|
| Milky | 当前版本 | HTTP / WebSocket | QQ 机器人应用接口标准，提供消息、事件、API 及 QQ 特性覆盖 |
| OneBot | v11 | HTTP / WebSocket / Webhook | 通用聊天机器人接口标准，v11 事件模型为传统格式 |
| OneBot | v12 | HTTP / WebSocket | 标准化事件结构和 API，与 v11 存在差异 |

关键协议约束：

- 消息定位依赖 `message_scene` + `peer_id` + `message_seq` 三元组（Milky 定义）。UniBot 内部统一模型采用 `normalized_scene + normalized_peer_id + normalized_message_seq`。对于 Milky，可直接映射 `message_scene + peer_id + message_seq`；对于 OneBot-v11/v12，由 Adapter 层转换或生成等价定位字段。若协议端无法提供稳定 seq，则系统应以协议端 `message_id` 或本地生成的 `normalized_message_id` 作为降级唯一标识
- 消息获取默认为分页式（Milky 单次默认 20 条，上限 30 条）
- 不同协议的字段命名、事件类型、错误码体系存在差异，需由 Adapter 层归一化
- 协议端可能不支持某些 QQ 资料实体的完整查询（如群文件、群相册），此时 UniBot 仅保存协议端实际返回的数据

### 3.2 运行环境与部署形态

| 项目 | 约束 |
|------|------|
| 操作系统 | Windows 10+ / macOS 12+ / Linux（主流发行版） |
| 部署形态 | 单机桌面应用，一个安装实例对应一个本地数据库 |
| 网络要求 | 仅需与本地或局域网内部署的协议端通信，无需访问互联网（协议端本身可能需要） |
| 硬件要求 | 2GB+ RAM，100MB+ 磁盘空间（不含协议包文件存储） |

### 3.3 技术栈约束与选型理由

| 层级 | 技术 | 选型理由 |
|------|------|----------|
| 桌面框架 | Tauri 2.x (Rust) | 内存占用低（相比 Electron），原生性能，安全的进程沙箱；Rust 的类型安全降低后端运行时错误 |
| 前端框架 | React 19 + TypeScript | 生态成熟，组件化开发效率高，TypeScript 提供类型安全 |
| 数据库 | SQLite（通过 Tauri 插件） | 嵌入式免安装，零配置，事务安全，支持部分索引和 CHECK 约束，适合本地桌面应用 |
| 大体积文件 | 本地文件系统（JSON 文件） | 协议包原始 JSON 体积大、访问频率低，存文件系统比 BLOB 更易管理和清理 |
| UI 组件 | shadcn/ui + Tailwind CSS 4 | 可定制、可访问性好、与 React 生态吻合 |
| 构建工具 | Vite 7 | 快速 HMR，与 React 和 Tauri 集成良好 |

选型的核心原则：**完全本地化** — 所有数据存储在本地，无需网络服务；**最小资源占用** — 桌面应用不应占用过多内存和 CPU。

> **注**：在开源版本文档中，本节精简为技术栈列表，不含选型论证细节。

### 3.4 假设与依赖

**假设 (Assumptions)：**

| 编号 | 假设内容 |
|------|----------|
| ASM-001 | 系统假设至少存在一个可用的 QQ 协议适配端（Milky 或 OneBot 实现），该端可通过 HTTP/WebSocket 与 UniBot 通信 |
| ASM-002 | 系统假设本地运行环境具有文件系统读写权限，且磁盘空间足以存储协议包文件 |
| ASM-003 | 系统假设协议端能够为每条消息提供可唯一定位的字段组合（至少包含 scene + peer_id + seq） |
| ASM-004 | 系统假设用户在单台计算机上使用 UniBot，不存在多用户并发访问同一数据库的场景 |
| ASM-005 | 系统假设模拟端（simulated）与真实端（real）的环境标识由用户或协议端明确提供，UniBot 不做自动推断 |

**外部依赖 (Dependencies)：**

| 编号 | 依赖内容 | 影响 |
|------|----------|------|
| DEP-001 | 依赖外部协议端提供消息事件、请求响应、账号/群组/好友资料等接口 | 若协议端不提供某接口，对应数据镜像能力受限 |
| DEP-002 | 依赖本地 SQLite 数据库和文件系统共同完成持久化 | 数据库或文件系统损坏可能导致数据丢失 |
| DEP-003 | 依赖协议端维护 `message_seq` 的单调递增性 | 若 seq 不单调，消息排序和去重逻辑需降级处理 |
| DEP-004 | 依赖 Tauri 运行时的 WebView 组件 | 不同操作系统的 WebView 版本差异可能影响 UI 渲染 |

### 3.5 外部接口需求概述

UniBot 通过以下接口与外部系统交互：

**3.5.1 协议适配器接口**

系统应能接收来自协议适配器（Milky / OneBot-v11 / OneBot-v12）的以下类型数据：

- **消息事件**：新消息到达通知，包含消息内容、发送者、会话标识
- **API 响应**：协议端对 Bot 发出的 API 调用的响应
- **状态事件**：Bot 连接状态、群成员变更、好友申请等业务事件
- **资料查询响应**：对好友资料、群资料、群成员列表等查询的响应

系统应能记录每次协议交互的请求-响应关联关系。当协议端字段缺失时，系统应保留原始协议数据并标记适配状态。

**3.5.2 本地文件系统接口**

系统需要读写以下文件：

- Bot 配置文件（JSON 格式，存储于 `configs/bots/` 目录）
- 协议包原始报文文件（JSON 格式，存储于 `data/packets/` 目录）
- 应用日志文件
- 缓存文件（头像、表情等）

系统应能读写本地文件；协议包原文在查看或导出时按 `file_path` 懒惰检测文件是否存在，文件缺失或不可读时给出明确提示。

**3.5.3 数据库接口边界**

SQLite 数据库通过 Tauri SQL 插件访问。数据库仅存储结构化索引字段和业务关系；大体积 JSON 内容（协议报文原文、消息段数组）的存储策略为"数据库存索引 + 文件系统存原文"。

## 5. 业务场景

### 5.1 Bot 开发者场景

**S-DEV-001：启动 Bot 并观察消息收发**

Bot 开发者在 UniBot 中启动一个已注册的 Bot 实例（绑定 QQ 账号）。系统建立与协议端的连接，开始新的调试会话。开发者向该 Bot 绑定的 QQ 号发送一条私聊消息。系统在会话列表中显示该私聊会话，在消息区域展示消息内容和发送者信息。开发者可以在消息详情中查看该消息对应的协议事件。Bot 的自动回复消息同样在会话中展示。

关联需求：FR-BOT-001, FR-MSG-001, FR-MSG-002, FR-DBG-001, FR-PKT-001

**S-DEV-002：从业务消息追溯到协议包**

开发者在群消息中看到一条异常回复。点击该消息的"查看协议包"，系统展示触发 Bot 响应的入站事件（inbound event）元数据：协议类型、action 名称、方向、时间。开发者可以进一步查看原始 JSON 报文，并关联查看 Bot 发出的 API 调用（outbound request）及其响应。

关联需求：FR-PKT-001, FR-PKT-002, FR-PKT-003, FR-MSG-005

**S-DEV-003：筛选失败的协议调用**

开发者在调试过程中发现 Bot 的部分消息没有发送成功。在协议包面板中，按 `is_error = true` 筛选，系统列出所有失败的协议调用，按时间倒序。开发者逐条查看失败的 action 名称、错误信息和原始请求/响应 JSON。通过这些信息，开发者定位到是 API 参数格式问题。

关联需求：FR-PKT-004, FR-DBG-003

**S-DEV-004：在模拟环境中测试 Bot 行为**

开发者启动内置虚拟服务端（simulated 环境），创建一个模拟 QQ 账号和模拟群组。将 Bot 指向模拟端后，手动在模拟客户端中发送群消息。系统记录模拟端的消息、协议包和调试会话，开发者可以像调试真实环境一样调试模拟场景，但数据与真实环境完全隔离。

关联需求：FR-ACC-001, FR-ACC-002, FR-SOC-003, FR-PKT-005

### 5.2 Bot 管理者场景

**S-ADM-001：创建并配置新 Bot 实例**

Bot 管理者在 UniBot 中注册一个新 Bot 实例。填写展示名称，选择一个已有的 IM 账号进行绑定。系统生成 Bot 唯一标识和默认配置文件。管理者可以在 Bot 详情中编辑连接配置（协议类型、WebSocket 地址、认证 token）和群组行为配置（禁言处理、消息回复策略等）。

关联需求：FR-BOT-001, FR-BOT-002, FR-CFG-001

**S-ADM-002：查看 Bot 运行状态和群组列表**

管理者的仪表盘展示所有 Bot 实例的运行状态（stopped / running / error）。选中一个运行中的 Bot，查看其绑定的群组列表，包括群名称、成员数、群内角色、配置启用状态。可以对群组进行分类标注，便于按分类管理 Bot 行为。

关联需求：FR-BOT-003, FR-SOC-001, FR-SOC-002, FR-CFG-003

**S-ADM-003：修改 Bot 配置并确认生效**

管理者修改某个群的 Bot 回复策略（如关闭自动回复），保存配置文件。系统记录配置变更的审计事件。Bot 下次收到该群消息时，新配置生效。管理者可以在审计日志中确认配置变更时间和内容。

关联需求：FR-CFG-002, FR-AUD-001

### 5.3 协议调试者场景

**S-DBG-001：按条件筛选协议包**

协议调试者需要对最近一小时的协议包进行全面排查。在协议包面板中，选择目标 Bot、时间范围、方向为"receive"，系统展示所有入站协议事件。调试者进一步筛选 action 名称为 `message.group` 的事件，系统展示所有群消息事件。调试者导出筛选结果的部分数据用于外部分析。

关联需求：FR-PKT-001, FR-PKT-004, FR-AUD-003

**S-DBG-002：重放或导出协议报文**

调试者对某个失败的 API 调用报文进行深入分析。查看完整的请求 JSON 和响应 JSON（从本地文件系统加载）。将其原始报文 JSON 文件导出到指定路径，或复制报文内容到剪贴板，用于在外部工具中重放或分析。

关联需求：FR-PKT-003, FR-AUD-003

**S-DBG-003：追踪多态业务关联**

调试者在查看群消息列表时，点击一条群通知（如入群申请），系统可从该通知跳转至产生通知的协议事件包。反过来，在查看协议包时，系统能显示该协议包关联的业务对象（如某条消息、某个群申请、某个群事件）。

关联需求：FR-PKT-002, FR-REQ-001

### 5.4 系统维护者场景

**S-MNT-001：清理历史协议包文件**

系统已运行数周，协议包文件占用了可观的磁盘空间。维护者设置数据保留策略（如保留最近 30 天的协议包），系统执行清理：先从协议包记录中确定待清理文件集合，删除对应数据库记录，并尝试删除磁盘 JSON 文件；若文件删除失败，生成清理待处理报告。清理后维护者验证数据库仍能正确关联消息和未被清理的协议包。

关联需求：FR-AUD-002, DR-CLN-001, DR-CLN-002

**S-MNT-002：检查数据库完整性与原文文件懒惰读取**

维护者触发数据库完整性检查。系统执行 SQLite `integrity_check`，并检查数据库中的 FK 引用是否有效、是否存在孤立记录。协议包原始 JSON 文件不做定时全量扫描；当用户查看或导出原文时，系统按 `protocol_packets.file_path` 读取文件，若文件缺失、不可读或解析失败，则在界面提示“文件已丢失或过期”。

关联需求：FR-AUD-004, NFR-REL-002

**S-MNT-003：备份和迁移数据库**

维护者需要迁移 UniBot 到新计算机。系统支持导出当前数据库和配置文件的完整备份包，或仅导出结构化数据（不含协议包文件）。在新计算机上，系统支持从备份包恢复数据库和配置。

关联需求：FR-AUD-005, NFR-MNT-003

| 关联场景 | S-DEV-004 |

| 验收标准 | 1. 在真实环境的会话列表中不会出现模拟环境的会话；2. 尝试将模拟账号加入真实群组时系统应阻止 |
| 关联数据域 | 身份与账号域 |

**FR-ACC-003：账号表情管理**

| 字段 | 内容 |
|------|------|

| 关联场景 | — |
| 前置条件 | 目标账号已存在 |

| 关联数据域 | 身份与账号域 |

### 6.2 Bot 实例管理 (FR-BOT)

**FR-BOT-001：Bot 注册与账号绑定**

**FR-BOT-002：Bot 运行状态管理**

**FR-BOT-003：Bot 仪表盘**

| 字段 | 内容 |

| 关联数据域 | 身份与账号域 |

### 6.3 会话与消息 (FR-MSG)

本子域是 UniBot 的核心功能域，定义消息收发、会话管理和消息互动需求。

**FR-MSG-001：消息接收与持久化**

| 字段 | 内容 |
|------|------|
| 描述 | 系统应接收来自协议适配器的消息事件，将消息存储到本地数据库，并按 scene（private/group/temp）+ peer_id + message_seq 唯一标识每条消息。消息内容以结构化 JSON 存储消息段数组。系统应同时存储发送者 ID、接收者 ID（私聊）、群 ID（群聊/临时会话）、引用消息 ID（如有）等关系字段。 |
| 优先级 | P0 |
| 关联角色 | R1 |
| 关联场景 | S-DEV-001 |
| 前置条件 | Bot 处于运行状态，协议端连接正常 |
| 后置条件 | 消息已持久化，关联会话已创建或更新 |
| 验收标准 | 1. Bot 收到一条私聊消息后，消息出现在对应会话中，message_seq 正确递增；2. 重复收到相同 scene+peer+seq 的消息时，系统应忽略（幂等性） |
| 关联数据域 | 会话消息域 |

**FR-MSG-002：会话列表管理**

| 字段 | 内容 |
|------|------|
| 描述 | 系统应按属主账号维护会话列表。会话类型包括 private（私聊）、group（群聊）、temp（临时会话）。每个会话应维护最近一条消息的引用、未读计数、最后已读序号、置顶和免打扰状态。会话列表按最后消息时间倒序排列。 |
| 优先级 | P0 |
| 关联角色 | R1, R2 |
| 关联场景 | S-DEV-001 |
| 前置条件 | 至少存在一条消息 |
| 后置条件 | 会话列表正确反映最新消息和未读状态 |
| 验收标准 | 1. 同一账号收到私聊和群聊消息后，会话列表分别出现 private 和 group 会话；2. 收到 3 条消息后未读数为 3；3. 标记已读后未读数归零 |
| 关联数据域 | 会话消息域 |

**FR-MSG-003：消息内容渲染**

| 字段 | 内容 |
|------|------|
| 描述 | 系统应能解析消息的 JSON 内容段数组，并渲染为可读消息内容。P0 范围包括 text 文本、at 提及和基础 reply 引用展示；P1 范围包括 image 图片预览、face 表情、自定义 Marketface 以及更复杂的富文本样式。 |
| 优先级 | P0（基础渲染）；P1（高级富文本渲染） |
| 关联角色 | R1 |
| 关联场景 | S-DEV-001 |
| 前置条件 | 消息已存储 |
| 后置条件 | 消息以可读的富文本形式展示 |
| 验收标准 | 1. (P0) 纯文本消息正确渲染；2. (P0) @消息可识别并高亮；3. (P0) 引用回复能显示被引用消息摘要；4. (P1) 图片消息能显示缩略图或资源占位；5. (P1) 系统表情和 Marketface 能显示对应占位或预览。 |
| 关联数据域 | 会话消息域 |

**FR-MSG-004：消息引用与撤回**

| 字段 | 内容 |
|------|------|
| 描述 | 系统应支持消息引用（reply）的展示和消息撤回（recall）的记录。引用消息被删除后，引用方仍可展示"已被撤回"占位。消息撤回时系统应标记 `is_recalled` 并记录撤回时间和操作者，而非物理删除消息记录。 |
| 优先级 | P1 |
| 关联角色 | R1 |
| 关联场景 | S-DEV-002 |
| 前置条件 | 引用消息或被撤回消息已存在 |
| 后置条件 | 引用关系或撤回状态已记录 |
| 验收标准 | 1. 展示引用消息时正确渲染被引用消息的摘要；2. 撤回消息后在该消息位置显示"已被撤回"；3. 引用消息被撤回后，引用方显示占位而非错误 |
| 关联数据域 | 会话消息域 |

**FR-MSG-005：消息与协议包的关联**

| 字段 | 内容 |
|------|------|
| 描述 | 系统应在消息存储时记录产生该消息的协议事件关联（通过 `bot_id` 反规范化字段 + 协议包的 `related_object_type`/`related_object_id`）。用户能从消息详情跳转至对应的协议包视图。 |
| 优先级 | P0 |
| 关联角色 | R1, R3 |
| 关联场景 | S-DEV-002 |
| 前置条件 | 消息由协议事件驱动产生，且对应的协议包已记录 |
| 后置条件 | 消息与协议包的关联可从任意一端追溯 |
| 验收标准 | 1. 点击消息的"查看协议包"，可打开对应的入站协议事件；2. 消息中的 bot_id 字段正确指向产生该消息的 Bot |
| 关联数据域 | 会话消息域, 协议调试域 |

**FR-MSG-006：消息表情回应**

| 字段 | 内容 |
|------|------|
| 描述 | 系统应记录消息的表情回应（reaction）。支持添加和移除操作（toggle 模式），不物理删除记录而使用 `is_add` 标记。 |
| 优先级 | P2 |
| 关联角色 | R1 |
| 关联场景 | — |
| 前置条件 | 目标消息已存在 |
| 后置条件 | 表情回应记录已添加或标记移除 |
| 验收标准 | 1. 收到 reaction add 事件后消息展示对应表情图标和计数；2. 收到 reaction remove 事件后计数减少；3. 同一用户对同一消息同一表情不可重复添加 |
| 关联数据域 | 会话消息域 |

**FR-MSG-007：戳一戳互动**

| 字段 | 内容 |
|------|------|
| 描述 | 系统应记录戳一戳（poke）互动，包括发起人、目标人、会话场景和时间。支持戳一戳撤回记录。 |
| 优先级 | P2 |
| 关联角色 | R1 |
| 关联场景 | — |
| 前置条件 | 会话已存在 |
| 后置条件 | 戳一戳互动已记录 |
| 验收标准 | 1. 收到戳一戳事件后，会话中显示戳一戳提示；2. 戳一戳被撤回后标记撤回状态 |
| 关联数据域 | 会话消息域 |

### 6.4 好友、群与成员资料镜像 (FR-SOC)

本子域定义对 QQ 社交关系数据的镜像缓存需求。UniBot 应按 Bot 调试、消息展示、行为模拟和协议追踪的需要，选择性缓存好友、群组、群成员及协议端返回的低频资料。系统不承诺与协议端强一致，也不承诺完整同步 QQ 客户端的全部社交数据。

**FR-SOC-001：群组资料镜像**

| 字段 | 内容 |
|------|------|
| 描述 | 系统应缓存群组的基本信息，包括群名称、群头像、群主、成员数、最大成员数、全员禁言状态、群来源（simulated/real）。群组应支持分类标注和置顶。 |
| 优先级 | P0 |
| 关联角色 | R1, R2 |
| 关联场景 | S-ADM-002 |
| 前置条件 | Bot 已绑定账号且有群聊消息或群资料查询 |
| 后置条件 | 群组信息已缓存 |
| 验收标准 | 1. Bot 收到群消息后，对应群组自动出现在群列表中；2. 群主信息、成员数正确展示；3. 全员禁言状态的变更被同步记录 |
| 关联数据域 | 社交资料域 |

**FR-SOC-002：群成员信息缓存**

| 字段 | 内容 |
|------|------|
| 描述 | 系统应缓存群成员的基础身份信息，并在协议端提供时缓存扩展信息。P0 范围包括成员账号标识、群名片和基础角色；P1 范围包括专属头衔、入群时间、最后发言时间和禁言状态等扩展字段。 |
| 优先级 | P0（基础身份）；P1（扩展资料） |
| 关联角色 | R1, R2 |
| 关联场景 | S-ADM-002 |
| 前置条件 | 群已存在 |
| 后置条件 | 成员信息已缓存 |
| 验收标准 | 1. (P0) 群成员列表展示各成员的群名片和基础角色（群主/管理员/普通成员）；2. (P1) 成员被禁言后禁言状态正确更新；3. (P1) 成员退群后成员列表更新；4. (P1) 专属头衔、入群时间、最后发言时间正确缓存 |
| 关联数据域 | 社交资料域 |

**FR-SOC-003：模拟/真实群组环境隔离**

## 7. 数据需求

### 7.1 数据域总览

本系统需求层划分为 **5 个数据域**。每个域定义了系统必须持久化的数据类别及其业务含义。每个功能需求的"关联数据域"字段指明了该需求涉及哪些域。具体的实体映射和表结构由数据库设计文档给出。

| 数据域 | 含义 | 关联功能域 | 核心实体概念 |
|--------|------|------------|--------------|
| **身份与账号域** | 外部 IM 账号身份信息、Bot 实例注册与绑定关系 | FR-ACC, FR-BOT | IM 账号、Bot 实例、账号表情、好友分组、群分类 |
| **会话消息域** | 消息、会话容器及消息级互动（引用、表情回应、戳一戳） | FR-MSG | 会话、消息、表情回应、戳一戳 |
| **社交资料域** | 好友关系、群组、群成员、群内容资产及社交请求与事件 | FR-SOC, FR-REQ | 好友、群、群成员、群公告、群文件、群相册、群精华、好友申请、群申请、群事件 |
| **协议调试域** | 协议报文索引与原始报文文件、调试会话聚合 | FR-PKT, FR-DBG | 协议包、原文文件路径、调试会话 |
| **系统治理域** | 应用设置、操作审计日志、数据清理与备份策略 | FR-CFG, FR-AUD | 应用设置、审计事件 |

### 7.2 核心业务数据

核心业务数据指系统核心流程（Bot 运行-消息收发-会话管理）直接依赖的数据：

- **IM 账号**：系统的身份基础，所有 Bot 绑定、消息归属、好友关系均以账号为主体
- **Bot 实例**：调试的目标对象，必须绑定一个 IM 账号
- **会话**：消息的组织容器，按属主账号 + 场景 + 对端标识唯一确定
- **消息**：核心资产，按 scene + peer_id + message_seq 唯一标识，内容以 JSON 段数组存储

这些数据必须保证 ACID 事务一致性。

### 7.3 协议调试数据

协议调试数据是 UniBot 区别于普通 IM 客户端的关键数据资产：

- **协议包**：每次协议交互的记录，存储结构化索引字段（协议类型、方向、action、错误标记），原始 JSON 存文件系统
- **原文文件路径**：每个协议包记录直接保存 `file_path`，查看或导出时按路径读取
- **调试会话**：Bot 运行周期的抽象，聚合消息和协议包

协议调试数据支持多态关联到业务对象（通过 `related_object_type` + `related_object_id`），但不建立 FK 约束（运行时决定引用目标）。

### 7.4 缓存与镜像数据

缓存与镜像数据源自外部协议端，系统被动接收并本地缓存。这些数据用于支撑展示和调试上下文，系统不承诺与协议端强一致性同步：

- **好友关系、群组、群成员**：展示和群组管理的基础资料
- **群公告、群文件/文件夹、群相册/照片、群精华消息**：低频镜像数据，均为 P1/P2 优先级
- **账号表情**：表情渲染缓存

缓存数据的原则：协议端返回什么就存什么，协议端不支持查询的实体不主动拉取。

### 7.5 系统配置与审计数据

- **应用设置**：保存全局 Key-Value 配置，包含当前 schema 版本、数据保留策略和 UI 偏好。具体迁移记录结构由数据库设计文档确定
- **审计事件**：所有关键操作的不可变记录
- **Bot 配置文件**：存储于文件系统的 JSON 文件，数据库仅存配置路径指针

### 7.6 数据生命周期

| 数据类别 | 创建时机 | 更新频率 | 删除策略 | 清理方式 |
|----------|----------|----------|----------|----------|
| 账号信息 | 首次同步或手动创建 | 低（资料变更时） | 手动删除；默认解除与历史消息的强引用，用户可选择彻底清除关联数据 | — |
| Bot 实例 | 手动注册 | 低（配置变更时） | 手动删除；运行态、配置指针和调试会话按策略处理 | — |
| 消息 | 协议消息事件到达时 | 高（按消息频率） | 默认不自动清理；支持用户手动删除或按账号执行彻底清除 | — |
| 会话 | 首条消息到达时 | 高（每条新消息更新） | 手动删除；默认仅删除会话视图状态，是否删除消息由用户操作决定 | — |
| 社交资料 | 协议事件驱动同步 | 中（资料/成员变更时） | 手动删除群组/好友；账号彻底清除时删除相关缓存 | — |
| 协议包 | Bot 运行时每次协议交互 | 极高 | 按保留策略定期清理 | 定时任务按 TTL 清理 |
| 协议包文件 | 协议包记录创建时同步写入 | 极少（仅写入一次） | 随协议包清理流程处理；删除失败时记录待清理报告 | 后台任务重试 |
| 调试会话 | Bot 启动时自动创建 | 低（结束时更新） | 手动删除；可保留摘要或按用户选择清理关联标记 | — |
| 审计事件 | 关键操作发生时 | 中 | 保留期内只追加、不修改、不由普通流程删除 | 按保留策略归档或清理 |

### 7.7 数据保留与清理策略

| 编号 | 内容 |
|------|------|
| DR-CLN-001 | 系统应支持配置协议包和协议包文件的保留天数（默认 30 天），超过保留期限的数据由定时任务自动清理 |
| DR-CLN-002 | 清理协议包时，系统应先从 `protocol_packets.file_path` 确定待清理文件集合，再删除数据库记录并尝试删除磁盘文件；若磁盘删除失败，应生成清理报告，由后台任务重试 |
| DR-CLN-003 | 消息记录默认不自动清理，由用户手动删除 |
| DR-CLN-004 | 普通操作审计事件默认保留 90 天，安全关键审计事件默认永久保留。超过保留期限的普通审计事件由定时任务自动清理 |
| DR-CLN-005 | 缓存与镜像数据（好友、群组、成员等）不自动清理，随关联的账号删除而 CASCADE 清除 |

## 8. 非功能需求

### 8.1 性能 (NFR-PERF)

**测试环境**：CPU 四核及以上，内存 8GB，存储 SSD，SQLite 开启 WAL 模式，查询使用已建立索引。统计口径：连续 10 次，取 P95 值。

| 编号 | 内容 |
|------|------|
| NFR-PERF-001 | 在本地 SQLite 数据库中，消息量达到 100 万条时，按会话加载最近 30 条消息的响应时间应 ≤ 300ms |
| NFR-PERF-002 | 协议包量达到 50 万条时，按 Bot + 时间范围（最近 7 天）筛选最近 100 条的响应时间应 ≤ 500ms |
| NFR-PERF-003 | 会话列表（最近 50 个会话）加载时间应 ≤ 300ms |
| NFR-PERF-004 | UI 界面在消息和协议包持续写入时，帧率应保持 ≥ 30 FPS |
| NFR-PERF-005 | 应用冷启动（含数据库连接）时间应 ≤ 2 秒 |

### 8.2 容量与可扩展性 (NFR-CAP)

| 编号 | 内容 |
|------|------|
| NFR-CAP-001 | 系统应支持注册至少 20 个 Bot 实例 |
| NFR-CAP-002 | 系统应在单个 SQLite 数据库文件中存储至少 100 万条消息而不出现显著的查询降级 |
| NFR-CAP-003 | 系统应在单个 SQLite 数据库文件中存储至少 50 万条协议包记录 |
| NFR-CAP-004 | 协议包文件应按日期、Bot ID 或 packet_id 前缀分片存储，系统总体应支持至少 50 万个协议包 JSON 文件（每个 1-500KB） |
| NFR-CAP-005 | 系统应支持缓存至少 500 个群组和 10 万个群成员记录 |

### 8.3 可靠性与恢复 (NFR-REL)

| 编号 | 内容 |
|------|------|
| NFR-REL-001 | 系统异常退出（进程崩溃、断电）时，不应破坏 SQLite 数据库文件的完整性（依赖 SQLite WAL 模式和原子提交） |
| NFR-REL-002 | 数据库记录引用协议包文件路径但磁盘文件缺失时，系统应在用户查看或导出原文时识别并提示异常，而非崩溃 |

| NFR-REL-004 | 协议包写入过程中发生异常，数据库不应留下指向未成功落盘 JSON 的协议包记录 |

### 8.4 安全与隐私 (NFR-SEC)

| 编号 | 内容 |
|------|------|
| NFR-SEC-001 | UniBot 自身生成的数据库字段、配置文件和日志文件不得主动写入明文登录凭据、Cookie 或认证 Token |
| NFR-SEC-002 | 协议端返回的原始协议包可能包含敏感字段（如 token、cookie），UniBot 不保证自动脱敏；系统应在导出、复制和共享协议包前提示用户检查内容并确认风险 |
| NFR-SEC-003 | 导出协议包数据前，系统应提示用户确认导出范围并警告可能包含隐私信息 |

| NFR-SEC-005 | 本地日志文件不应输出消息内容、协议包原始 JSON 或任何可能包含用户聊天内容的文本字段 |

## 10. 不做范围

以下条目明确了 UniBot 系统边界，作为需求的硬性排除项。

| 编号 | 内容 |
|------|------|
| OUT-001 | 系统不保证完整同步 QQ 客户端的全部历史消息，仅保存 UniBot 运行期间通过 Bot 接收或主动拉取的消息 |
| OUT-002 | 系统不作为长期聊天记录归档工具，历史协议包按保留策略自动清理 |
| OUT-003 | 系统不保证群文件、群相册、群公告等低频资料的强一致性镜像，仅作为协议端返回数据的被动缓存 |
| OUT-004 | 系统不直接管理或存储 QQ 登录凭据（password、ticket、token 等），这些由外部协议端自行管理 |
| OUT-005 | 系统不保证跨协议端（Milky/OneBot-v11/OneBot-v12）的字段完全一致，协议差异由 Adapter 层尽力归一化 |
| OUT-006 | 系统不提供多用户协作功能，单个 UniBot 实例为单用户本地使用设计 |
| OUT-007 | 系统不是 QQ Bot 的托管平台：不提供 Bot 的云端部署、不管理 Bot 的生命周期自动恢复、不提供 Bot 运行监控告警 |
| OUT-008 | 系统不自动执行 Bot 行为：消息回复、群管理、好友审批等均由 Bot 自身（外部协议端）执行，UniBot 仅记录和展示 |

## 11. 验收与验证策略

### 11.1 P0 需求验收原则

所有 P0 需求必须满足以下验收原则：

1. **每项可独立验证**：不依赖其他未完成的 P0 需求
2. **验收条件可执行**：验收标准表述为可观察、可测量的结果
3. **边界条件覆盖**：至少包含正常路径和至少一个异常/边界路径
4. **数据一致性**：涉及数据写入的需求，必须包含"数据库记录与界面展示一致"的验证

### 11.2 场景级验收用例

| 场景编号 | 验收用例描述 |
|----------|-------------|
| S-DEV-001 | **端到端验收**：注册一个 Bot，绑定真实账号，启动 Bot，向该账号发送一条私聊消息：(a) 会话列表中显示该私聊会话；(b) 消息内容正确展示；(c) 调试会话已创建；(d) 协议包列表中包含对应的入站事件 |
| S-DEV-002 | **关联追溯验收**：选中一条群消息，点击"查看协议包"，系统跳转至对应的协议包详情，展示协议类型、action 名称和原始 JSON |
| S-DEV-003 | **错误筛选验收**：构造 3 个 Bot、2 个调试会话、若干正常包和失败包，按 is_error=true 筛选，结果仅包含失败包 |
| S-DEV-004 | **环境隔离验收**：创建模拟账号和模拟群，启动模拟端，发送群消息：(a) 真实环境的会话列表不含模拟群会话；(b) 模拟群的成员不包含真实账号 |
| S-ADM-001 | **Bot 创建验收**：注册新 Bot，填写展示名称，选择绑定账号，保存后：(a) Bot 列表显示新 Bot；(b) 点击可见详情；(c) 配置文件已创建 |
| S-ADM-003 | **配置变更验收**：修改 Bot 群组行为配置（关闭自动回复），保存：(a) 配置文件内容已更新；(b) 审计事件已记录；(c) Bot 重启后新配置生效 |
| S-DBG-001 | **多维筛选验收**：选择特定 Bot + 最近 24 小时 + 方向 receive + action 包含 "message"，结果仅展示匹配项 |
| S-MNT-001 | **数据清理验收**：设置保留 7 天，系统有 10 天前的协议包，执行清理：(a) 10 天前的协议包记录删除；(b) 对应磁盘 JSON 文件删除；(c) 7 天内的协议包保留完整 |
| S-MNT-002 | **懒惰读取验收**：手动删除一个协议包 JSON 文件，点击该协议包的“查看原文”：(a) 系统不崩溃；(b) 界面提示文件已丢失或过期 |

### 11.3 数据一致性验收

| 编号 | 验收内容 |
|------|----------|
| V-DC-001 | 报文写入一致性：写入 1000 条协议包的压测中，数据库协议包记录数 = 磁盘 JSON 文件数，且每条记录的 file_path 可定位到对应文件 |
| V-DC-002 | 消息幂等性：重复发送相同 scene+peer+seq 的消息事件 100 次，数据库中仅存在 1 条消息记录 |
| V-DC-003 | 账号删除一致性：删除 IM 账号后，历史消息的 sender 引用被置空且消息内容保留；Bot 绑定、好友关系、会话状态和缓存数据按删除策略正确处理；当用户选择“彻底清除”时，该账号相关的消息、会话、缓存和协议关联数据被清理或脱敏 |
| V-DC-004 | 未读计数：在同一会话中连续接收 N 条消息后，unread_count = N；执行标记已读后，unread_count = 0 |

### 11.4 非功能需求验收

| 编号 | 验收内容 |
|------|----------|
| V-NFR-001 | 性能：100 万条消息库中，按会话加载最近 30 条消息，使用 `performance.now()` 计时，连续 10 次取 P95 值 ≤ 300ms |
| V-NFR-002 | 可靠性：在消息写入过程中强制终止进程，重启后数据库用 `PRAGMA integrity_check` 验证无损坏 |
| V-NFR-003 | 安全：使用敏感字段字典（token、cookie、ticket、authorization、session、credential、access_token、refresh_token 等）扫描数据库字段、配置文件、应用日志和导出文件；确认 UniBot 自身不会主动写入明文凭据。对原始协议包文件，仅验证导出前风险提示和用户确认流程 |
| V-NFR-004 | 兼容性：分别连接 Milky 和 OneBot-v11 协议端，发送同样内容的群消息，两条消息在 UniBot 中均正确展示基本内容（文本、发送者），协议特有字段标记来源 |
