# UniBot 数据库系统需求分析报告

---

## 1. 课题背景与问题定义

QQ Bot 开发过程中，消息、协议事件、Bot 配置、群组资料和调试日志分散在不同工具中，开发者难以追踪"某条消息是否被 Bot 收到、对应哪个协议事件、Bot 是否发出了响应"。当前面临的核心痛点：

1. **协议黑盒**：协议请求/响应对开发者不可见，难以定位"消息发不出去""事件没收"等问题的根因。
2. **多 Bot 管理混乱**：一个开发者同时维护多个 Bot，绑定不同账号、配置和群组，缺少统一管理界面。
3. **消息与协议割裂**：当 Bot 未回复某条消息时，开发者需人工关联消息、协议事件和 API 调用。

UniBot 旨在构建一个本地化多 Bot 调试与管理平台，通过数据库统一保存账号、Bot、会话、消息、协议包索引和审计数据，为消息追踪、协议调试和系统管理提供数据基础。

---

## 2. 系统目标与用户角色

### 2.1 用户角色

| 编号 | 角色 | 核心需求 |
| ------ | ------ | ---------- |
| R1 | Bot 开发者 | 调试消息收发、协议事件和 API 调用 |
| R2 | Bot 管理者 | 管理多个 Bot、账号绑定、配置和群组策略 |
| R3 | 协议调试者 | 查看协议请求、响应、事件和错误包 |
| R4 | 系统维护者 | 负责数据清理、审计、备份和一致性检查 |

### 2.2 系统目标

1. 管理多个 Bot 实例及其绑定账号
2. 保存会话、消息和社交资料缓存
3. 建立消息与协议包之间的追踪关系
4. 支持本地审计、数据清理和后续数据库设计

---

## 3. 主要业务场景

### **S1：创建 Bot 并启动调试会话**

开发者注册 Bot，绑定 QQ 账号。启动 Bot 后系统自动创建调试会话，后续消息和协议包均归入该会话。

### **S2：接收消息并更新会话列表**

Bot 收到私聊或群聊消息，系统持久化消息并自动创建或更新会话（最后消息、未读计数），会话列表按最后消息时间倒序排列。

### **S3：从消息追溯到协议包**

开发者在消息中点击"查看协议包"，系统展示触发该消息的入站协议事件（协议类型、action、方向、时间），并可查看原始 JSON 报文及关联的 API 调用。

### **S4：管理 Bot 状态与群组配置**

管理者在仪表盘查看所有 Bot 运行状态、绑定的群组和成员概况，按群修改 Bot 回复策略。

### **S5：清理历史协议包**

维护者设置保留策略（默认 30 天），系统定时清理超期协议包的数据库记录和磁盘文件。消息记录不受影响，清理操作记录审计日志。

---

## 4. 功能需求

### 4.1 账号与 Bot 管理

系统应支持记录 IM 账号信息（昵称、头像、来源标记）和 Bot 实例信息（名称、运行状态、关联账号）。一个 Bot 绑定一个账号，一个账号最多绑定一个 Bot。账号分为模拟端（simulated）和真实端（real），数据在逻辑上隔离。Bot 配置文件存储于文件系统，数据库仅保存配置路径。

### 4.2 会话与消息管理

系统应支持私聊（private）、群聊（group）、临时会话（temp）三种场景。会话按属主账号 + 场景 + 对端标识唯一确定，维护最后消息、未读计数、置顶和免打扰状态。消息按 scene + peer_id + message_seq 三元组唯一标识，支持幂等性。内容以 JSON 段数组存储，支持文本、@提及、引用回复的渲染。消息撤回以标记实现（不物理删除），支持消息与协议包双向关联。

### 4.3 社交资料缓存

系统应缓存群组信息（名称、头像、群主、成员数）和群成员身份（群名片、角色）。好友关系以属主视角保存，含备注名、分组和置顶。群分类和好友分组均为 per-user 归属，不可作为群或好友的全局属性。此外被动缓存群公告、群文件和群精华等低频资料。缓存原则：协议端返回什么就存什么，不承诺强一致。

### 4.4 协议包追踪

系统应记录用于调试追踪的协议交互元数据（协议类型、方向、action、Bot、调试会话、错误标记、时间戳）。原始 JSON 存文件系统，数据库仅存结构化索引和 `file_path`。支持协议包与业务对象的多态双向关联，支持按 Bot、方向、action、错误状态、时间范围组合筛选，支持原始报文查看和导出。

### 4.5 调试会话管理

Bot 启动时自动创建调试会话，停止时记录结束时间。消息和协议包标记所属会话 ID，可回看历史会话的消息和协议包。

### 4.6 审计与维护

系统应记录关键操作的审计事件（Bot 启停、配置变更、数据删除等）。协议包按保留策略定时清理。支持数据导出，导出前提示用户检查敏感信息。支持应用设置 Key-Value 存储（schema 版本、保留天数等）。

## 5. 数据需求

系统数据划分为 5 个域：

### 5.1 身份与配置域

包括 IM_ACCOUNT、BOT、账号头像/表情缓存等。账号的 `account_source` 区分 simulated / real 环境，Bot 通过外键绑定唯一账号。

### 5.2 社交与群组域

包括好友关系、好友分类、CHAT_GROUP（群本身）、GROUP_MEMBER、GROUP_CATEGORY（per-user，账号自定义群分类）、USER_GROUP（账号视角下的群关系）、群公告、群文件、群相册和 GROUP_EVENT 等。

关键设计点：CHAT_GROUP 是群的客观属性；USER_GROUP 是某账号视角下的主观关系（置顶、分类）；GROUP_CATEGORY 是账号自定义分类体系。三者分离才能满足 3NF。

### 5.3 会话与消息域

包括 CONVERSATION 和 MESSAGE。CONVERSATION 维护会话级状态，MESSAGE 保存归一化后的消息事实。消息是核心调试资产，其写入应与会话更新、协议包索引写入保持事务一致性。

### 5.4 协议调试域

包括 DEBUG_SESSION（Bot 运行周期）和 PROTOCOL_PACKET（协议包索引与原文文件路径）。协议包原文存文件系统，数据库仅保存结构化索引和 `file_path`。通过 `related_object_type` + `related_object_id` 实现多态业务关联。

### 5.5 系统治理域

包括 APP_SETTING（Key-Value 应用设置）和 AUDIT_EVENT（审计事件）。审计事件在保留期内只追加、不可修改；超出保留期后按清理策略处理。

### 5.6 数据库规范化

数据库设计将尽量满足第三范式（3NF）：非主属性应直接依赖于候选键而非其他非主属性，避免插入、删除和更新异常。若为查询性能保留少量冗余字段（如消息表的 `bot_id`），需在数据库设计文档中说明理由和影响。

## 6. 非功能需求与约束

**数据库平台**：本项目课程实现采用 SQLite。课程默认推荐 MySQL，但经与任课教师沟通，本项目可根据实际需求选择 SQLite。UniBot 定位为本地化多 Bot 调试与管理平台，主要运行在单机桌面环境中，数据访问集中在本地客户端，不需要独立数据库服务器或多用户远程并发访问。相比 MySQL 的客户端-服务器部署方式，SQLite 以嵌入式、零配置、单文件数据库形式运行，更符合本项目的本地调试工具定位。数据库设计层面仍采用关系模型，后续将给出 ER 图、关系模式、主外键约束、唯一约束、索引、触发器和 3NF 分析，不影响本课程对需求分析、概念设计、逻辑设计和规范化分析的要求。

**性能**：设计上应支持百万级消息、数十万级协议包下的分页和筛选查询；课程演示阶段可使用较小规模测试数据验证查询路径和索引有效性。

**可靠性**：核心结构化数据通过数据库事务保证一致性；消息写入、会话更新和协议包索引写入应尽量处于同一事务边界内。协议包记录直接保存 `file_path`；查看或导出原文时按路径读取，文件缺失或不可读时提示异常而非崩溃。

**隐私安全**：系统不主动写入明文凭据；导出协议包前提示用户检查敏感内容；删除账号时历史消息 sender 置空且保留内容，用户可选择彻底清除。

**可维护性**：实体划分清晰，数据访问层与协议适配层保持独立接口边界，便于后续 ER 图、关系模式、索引和测试用例设计。

---

## 7. 系统边界与后续数据库设计依据

UniBot 不作为完整 QQ 客户端替代品，不保证同步全部历史消息，也不作为长期聊天归档工具。群文件、群公告等资料主要作为 Bot 调试上下文缓存，不承诺与协议端强一致。系统不直接管理 QQ 登录凭据，不提供多用户协作功能。

系统重点是围绕 Bot 调试建立账号、Bot、会话、消息、协议包之间的核心数据关系，支撑"从消息追溯到协议包"的全链路调试体验。

后续概要设计将基于上述需求建立 ER 模型，重点描述 IM_ACCOUNT、BOT、CONVERSATION、MESSAGE、CHAT_GROUP、USER_GROUP、PROTOCOL_PACKET、DEBUG_SESSION、AUDIT_EVENT 等核心实体及其关系；数据库逻辑设计将进一步给出关系模式、主外键约束、索引设计和 3NF 分析。000
